# Flipkart Order Intelligence & Support Assistant

An end-to-end machine learning and agentic AI system for Flipkart support operations.

The project connects three components:

1. Return-risk scoring for orders
2. Product-image classification
3. A support assistant that can use both trained models and a grounded policy knowledge base

# Part 1 - Return-Risk Scoring Pipeline

Part 1 generates a deterministic order-history dataset, preprocesses it without test leakage, trains a baseline and machine-learning models, evaluates the winning Random Forest, and saves the final trained pipeline for Part 3.

## Dataset

The dataset is generated by:

```bash
python part1_return_risk/generate_orders.py
```

The generator uses the required fixed random seed:

```text
np.random.default_rng(42)
```

The generated dataset is saved to:

```text
part1_return_risk/orders_dataset.csv
```

## Preprocessing

The return-risk pipeline uses scikit-learn `ColumnTransformer` and `Pipeline`.

Numeric features use median imputation followed by standard scaling.

Categorical features use most-frequent imputation followed by one-hot encoding.

The preprocessing pipeline is fitted on the training split only and then applied to the held-out test split.

## Models

A most-frequent `DummyClassifier` is used as the baseline.

The main models are:

- Logistic Regression with `class_weight="balanced"`
- Random Forest with `class_weight="balanced"`

The tuned Random Forest uses:

```text
n_estimators = 200
max_depth = 6
random_state = 42
```

The tuned Random Forest is the final model used by Part 3.

## Random Forest Threshold

The Random Forest's F1-maximising threshold on its own `predict_proba` output is:

```text
t*_rf = 0.50
```

The Part 3 risk buckets are anchored to this threshold:

```text
Low: probability < 0.50
Medium: 0.50 <= probability < 0.65
High: probability >= 0.65
```

This keeps the risk buckets relative to the probability scale of the actual trained Random Forest rather than using unrelated fixed cut points.

## Saved Model

The final fitted preprocessing pipeline and tuned Random Forest are saved to:

```text
models/return_risk_model.pkl
```

This exact saved artifact is loaded by Part 3's `check_return_risk` tool.

# Part 2 - Product Image Categoriser

Part 2 uses the real Fashion-MNIST benchmark dataset and a pretrained ResNet-18 transfer-learning pipeline.

## Dataset

Fashion-MNIST is downloaded automatically with torchvision.

The pipeline uses:

- 55,000 training images
- 5,000 validation images
- 10,000 untouched test images
- 10 classes

The dataset source is:

https://github.com/zalandoresearch/fashion-mnist

## Preprocessing

The original Fashion-MNIST images are grayscale 28x28 images.

They are processed by:

- Replicating the grayscale channel to 3 channels
- Resizing to 224x224
- ImageNet normalization

ImageNet mean:

```text
[0.485, 0.456, 0.406]
```

ImageNet standard deviation:

```text
[0.229, 0.224, 0.225]
```

## Transfer Learning

The model uses a pretrained ResNet-18 CNN backbone.

During feature extraction, the ResNet-18 backbone is frozen and its 512-dimensional output features are cached.

A new 10-class classifier head is trained on the cached features.

Training configuration:

- Optimizer: Adam
- Learning rate: 0.001
- Head batch size: 256
- Maximum head epochs: 10
- Early stopping patience: 3

The classifier predicts:

1. T-shirt/top
2. Trouser
3. Pullover
4. Dress
5. Coat
6. Sandal
7. Shirt
8. Sneaker
9. Bag
10. Ankle boot

## Fine-Tuning

The feature-extraction model exceeded the required validation threshold, so fine-tuning was not required for the final reported model.

## Final Test Results

The final model was evaluated on the untouched 10,000-image test split.

Final test accuracy:

```text
88.61%
```

This exceeds the required 80% held-out test accuracy.

## Main Confusion Patterns

### Shirt -> T-shirt/top

There were 126 errors where a true Shirt image was classified as T-shirt/top.

Shirts and T-shirts/top items can have similar upper-body silhouettes in the low-resolution Fashion-MNIST images. Both may appear as a simple torso shape with sleeves extending from the sides. Details such as collars, buttons, and fabric structure are difficult to distinguish at low resolution, which makes this confusion plausible.

### Shirt -> Coat

There were 104 errors where a true Shirt image was classified as Coat.

Shirts and coats can also share similar torso and sleeve outlines. In a small grayscale image, details such as garment length, collar structure, and front opening may not be represented clearly enough for perfect classification. This makes Shirt -> Coat a plausible confusion pattern.

# Part 3 - Flipkart Support Agent

Part 3 connects the Part 1 return-risk model, the Part 2 product-image classifier, and a local policy knowledge base into one LangGraph support assistant.

## Part 3 Architecture

The assistant uses the following flow:

```text
User message
    |
    v
Input guardrail
    |
    v
Intent classification
    |
    v
Conditional routing
    |
    +--------------------+----------------------+
    |                    |                      |
    v                    v                      v
Policy RAG          Return-risk tool       Image tool
    |                    |                      |
    +--------------------+----------------------+
                         |
                         v
                Response generation
                         |
                         v
                Structured JSON
```

The graph contains six nodes:

- `input_guardrail`
- `intent`
- `policy_retrieval`
- `return_risk_tool`
- `product_image_tool`
- `response`

Conditional edges route requests according to intent:

- `policy` -> policy retrieval
- `return_risk` -> Part 1 return-risk tool
- `product_category` -> Part 2 image-classifier tool

## Policy Knowledge Base

The knowledge base contains 14 project-authored policy documents.

Each policy document contains multiple sentences and is split sentence-wise into 28 chunks.

Each chunk retains its parent `document_id` so retrieval evaluation can be performed at the document level.

The main policy topics include:

- apparel and footwear returns
- electronics returns
- home-product returns
- COD refunds
- prepaid refunds
- delivery SLAs
- delayed delivery
- reverse pickup
- damaged products
- wrong products
- non-returnable items
- refund after reverse pickup
- replacement eligibility
- return-condition requirements

## Embedding and Vector Search

Policy chunks are embedded locally using:


## Prompt Engineering

The response generator uses role prompting and the 4S principles.

### Role

```text
You are Flipkart's support assistant. Answer customer questions using only the provided policy evidence or real tool results. Do not invent policies, order information, or product classifications.
```

### Specific

Use the customer's exact request, retrieved policy chunks, and tool outputs. Return only information supported by those inputs.

### Short

Keep the final response concise and focused on the customer's immediate support question.

### Surround

Treat retrieved policy text and tool results as the trusted context surrounding the answer. Do not use unsupported outside facts.

### Single

Produce one final structured response with exactly one answer, one source, and one confidence value.

The default response-generation mode is deterministic `MOCK_LLM`.

It requires:

- no API key
- no paid LLM service
- no outbound LLM request

The output schema is:

```json
{
  "answer": "string",
  "source": "policy_kb | return_risk_tool | image_classifier_tool",
  "confidence": 0.0
}
```

## Guardrails

### Input-side Prompt Injection

The agent detects input patterns such as:

```text
ignore previous instructions
ignore all rules
pretend you are...
```

and blocks the request.

Verified result:

```text
I can't follow requests that attempt to override my instructions.
```

### Output-side Groundedness

Policy answers require retrieved evidence with a minimum similarity threshold of:

```text
0.45
```

Verified ungrounded-query result:

```text
Best similarity: 0.2450
Threshold: 0.45
Grounded: False
```

The agent then refuses to fabricate a policy:

```text
I don't have sufficiently similar policy information in the knowledge base to answer that safely.
```

## Conversational State

Short-term conversational state carries an order ID across turns within the same conversation.

Example:

```text
Turn 1:
My order ORD2007 is delayed.

Turn 1 state:
{'order_id': 'ORD2007', 'intent': 'policy', 'user_message': 'My order ORD2007 is delayed.'}

Turn 2:
What can I do about that order?

Turn 2 state:
{'order_id': 'ORD2007', 'intent': 'policy', 'user_message': 'What can I do about that order?'}
```

The same follow-up in a freshly started conversation correctly has no previous order state:

```text
Fresh state:
{'order_id': None, 'intent': 'policy', 'user_message': 'What can I do about that order?'}
```

The fresh conversation responds:

```text
I don't have an order ID in this conversation. Please provide the order ID so I can help with that specific order.
```
